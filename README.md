# Паралельне розв'язання СЛАР методом Гаусса

Лабораторна робота №2: багатопотоковий застосунок на Haskell, який розв'язує
систему лінійних алгебраїчних рівнянь (СЛАР) паралельним варіантом методу
Гаусса.

Застосунок читає розширену матрицю системи, виконує прямий хід методу Гаусса
з частковим вибором головного елемента, паралельно оновлюючи незалежні рядки,
а потім виконує зворотну підстановку. Передбачені послідовний режим,
порівняльний benchmark, генератор тестових систем і докладна обробка помилок.

## Формати вхідних даних

### Матриця у файлі або `stdin`

Підтримується **розширена матриця** (augmented matrix) розміру `n × (n + 1)`:

```text
n
a11 a12 ... a1n b1
a21 a22 ... a2n b2
...
an1 an2 ... ann bn
```

Правила:

- перше значуще число — додатний цілий розмір системи `n`;
- далі має бути рівно `n * (n + 1)` чисел;
- числа розділяються будь-якими пробільними символами, тому рядки можна
  переносити довільно;
- порожні рядки ігноруються;
- усе після символу `#` у рядку є коментарем;
- десятковий роздільник — крапка; підтримуються експоненційні записи
  (`1e-3`, `+2.5E+4`);
- `NaN`, `Infinity`, `-Infinity` відхиляються;
- підтримується UTF-8 BOM на початку файлу;
- максимальний розмір вхідної матриці — `10000`;
- система має бути квадратною; окремі формати `A` та `b`, CSV з комами,
  комплексні числа й прямокутні системи не підтримуються.

Приклад (`examples/simple3.txt`):

```text
# Приклад 3x3: розв'язок (2, 3, -1)
3
2  1 -1   8
-3 -1  2 -11
-2  1  2  -3
```

Запуск:

```bash
cabal run parallel-gauss-solver -- examples/simple3.txt
cabal run parallel-gauss-solver -- --seq examples/simple3.txt
cat examples/simple2.txt | cabal run parallel-gauss-solver -- --seq
```

### Згенерована система

Режим `--gen N` створює строго діагонально домінантну систему `N × N` з
псевдовипадковими коефіцієнтами в `[-1, 1]`. Діагональний елемент більший за
суму модулів позадіагональних елементів рядка, тому матриця гарантовано
невироджена. Правий вектор обчислюється з відомого розв'язку, що дозволяє
перевірити точність.

```bash
cabal run parallel-gauss-solver -- --gen 500 --seed 42
cabal run parallel-gauss-solver -- --bench --gen 1200 --repeat 3 +RTS -N8
```

`N` для генератора — від 1 до 2000. `--seed` — невід'ємне ціле число.

### Чому саме така архітектура

- **Functional core / imperative shell.** Парсинг, модель даних, генератор і
  перевірки залишаються чистими. Мутабельні масиви та потоки зосереджені в
  обчислювальному ядрі й `Main`.
- **Один плоский масив замість списку рядків.** Під час елімінації
  створюється велика кількість проміжних значень. Плоский `IOUArray`/`STUArray`
  дозволяє оновлювати рядки на місці, не створюючи нових списків і не
  навантажуючи GC.
- **Спільний алгоритм для обох режимів.** Послідовний і паралельний варіанти
  використовують однакові кроки елімінації та зворотну підстановку; різниця
  лише в тому, хто виконує незалежні оновлення рядків.
- **Постійний пул потоків.** Створювати потоки на кожному кроці елімінації
  дорого: для `n=1200` це було б близько 1200 бар'єрів і тисячі потоків.
  Пул створюється один раз на розв'язання.
- **Помилки як значення.** Замість `error`/`fromJust` використовуються
  `Either InputError a` і `Either SolveError a`; `Main` перетворює їх у
  зрозумілі повідомлення та коди виходу.
- **Мінімум залежностей.** Немає `parallel`, `async`, `vector` або зовнішніх
  BLAS: для лабораторної достатньо `base` і `array`.

### Модель потоків

1. `getNumCapabilities` повертає кількість capabilities, увімкнених `+RTS -N`.
2. Якщо capability одна, застосунок свідомо виконує послідовний алгоритм.
3. Інакше `withWorkerPool` створює постійний пул із `forkIO`-потоків.
4. На кожному кроці прямий хід:
   - головний потік шукає головний елемент і переставляє рядки;
   - рядки нижче діляться на 2 × кількість потоків шматків;
   - кожен worker оновлює свій набір рядків на місці;
   - головний потік чекає на всі `MVar` — це бар'єр;
   - після бар'єра всі записи видимі наступному кроку.
5. Зворотна підстановка виконується послідовно, бо кожне `x[i]` залежить від
   вже знайдених `x[i+1..n-1]`.

Рядки, які оновлюються різними потоками, не перетинаються; головний рядок
лише читається. Це виключає гонки даних. Виняток у worker перехоплюється,
передається в головний потік і завершує розв'язання з помилкою.

## Алгоритм

Розширена матриця зберігається як один масив `n × (n + 1)`.

```text
for k = 0 .. n-1:
    p = argmax |a[i][k]| для i >= k          -- послідовно
    if |a[p][k]| < eps: вироджена система
    swap(a[k], a[p])

    for i = k+1 .. n-1:                       -- паралельно
        factor = a[i][k] / a[k][k]
        a[i][j] = a[i][j] - factor * a[k][j], j = k..n
        a[i][k] = 0

x[n-1] = a[n-1][n] / a[n-1][n-1]
for i = n-2 .. 0:
    x[i] = (a[i][n] - sum_{j>i} a[i][j] * x[j]) / a[i][i]
```

Складність:

- час — `O(n³)`;
- пам'ять — `O(n²)`;
- прямий хід дає основне навантаження, зворотна підстановка — `O(n²)`.

Частковий вибір головного елемента зменшує похибку та ризик ділення на дуже
мале число. Поріг `eps` (типово `1e-12`) вважає такий елемент виродженим.

### Паралелізація та її межі

- На кроці `k` оновлюються `n-k-1` незалежних рядків; це природний рівень
  паралелізму.
- Паралельний режим вмикається лише за достатнього обсягу роботи: не менше
  32 рядків і 50 000 клітинок. Інакше накладні витрати на синхронізацію
  більші за користь.
- Кількість шматків — `2 × capabilities`; це дає балансування, якщо один
  worker стартує пізніше.
- Пізні кроки елімінації мають мало роботи, тому виконуються послідовно.
- Зворотна підстановка й пошук головного елемента залишаються послідовними.
  Через закон Амдала прискорення на 8 ядрах не дорівнює 8×; для великих
  систем вдалося отримати понад 7×, на середніх — приблизно 3–6×.

## Бенчмарки

Вимірювання на цій машині: 8 ядер, GHC 9.6.7, macOS 27.2. Методика:

- системи генеруються `--gen N --seed 42`;
- `--repeat 2`, береться найкращий час після прогріву;
- послідовний час — окремий процес із `+RTS -N1`;
- паралельний час — окремий процес із `+RTS -N8`;
- таймер — `GHC.Clock.getMonotonicTimeNSec`, вимірюється лише розв'язання,
  без парсингу й генерації.

| n | Послідовно, `-N1`, мс | Паралельно, `-N8`, мс | Прискорення |
|---:|---:|---:|---:|
| 600 | 308.464 | 82.794 | **3.73×** |
| 1200 | 2339.630 | 391.792 | **5.97×** |
| 2000 | 10794.224 | 1471.676 | **7.33×** |

Відтворити:

```bash
./scripts/benchmark.sh
SIZES="800 1600" REPEAT=3 ./scripts/benchmark.sh
```

У самому процесі `--bench` також показує прискорення, але для чесного
порівняння краще брати послідовний час із `-N1`, а паралельний — із `-N8`:
у процесі з `-N8` послідовний режим теж отримує паралельний GC, тому його
час може бути заниженим. Для дуже малих систем, де час нижчий за роздільну
здатність таймера, замість прискорення виводиться `n/a`.

Прискорення не є лінійним: пошук головного елемента та зворотна підстановка
послідовні, пізні кроки елімінації мають мало роботи, а на малих системах
домінують накладні витрати на синхронізацію. На `n=2000` вдалося отримати
`7.33×` на 8 ядрах (у попередніх прогонах — приблизно `6.5–7.7×`).

Перевірити, що задіяні кілька capabilities:

```bash
cabal run parallel-gauss-solver -- --bench --gen 1200 --repeat 1 +RTS -N8 -s
```

У виводі RTS буде `using -N8` і `TASKS`; оскільки паралелізм зроблено через
`forkIO`, а не через `par`/sparks, статистика `SPARKS` буде нульовою — це
очікувано.

| Порожній ввід | повідомлення про очікуваний формат | 1 |
| Нецілий або недодатний `n` | `InvalidSize` з номером рядка | 1 |
| `n > 10000` | повідомлення про ліміт | 1 |
| Неправильна кількість чисел | очікувана й фактична кількість | 1 |
| Не число | номер рядка й токен | 1 |
| `NaN`, `Infinity` | відмова з номером рядка | 1 |
| Файл не знайдено / немає доступу | `не вдалося прочитати файл` | 1 |
| Невідома опція | коротке пояснення й usage | 1 |
| Некоректний `--eps`, `--repeat`, `--gen`, `--seed` | пояснення допустимого діапазону | 1 |
| `--seq` разом із `--bench` | конфлікт режимів | 1 |
| `--gen` разом із файлом | конфлікт джерела даних | 1 |
| Два вхідні файли | дозволено лише один | 1 |
| Вироджена матриця / нульовий провідний елемент | `SingularPivot` із кроком | 2 |
| `NaN`/нескінченність у процесі обчислень | `NonFiniteResult` | 2 |
| Паралельний результат розійшовся з послідовним у `--bench` | явна помилка | 2 |
| Непередбачений виняток | `Непередбачена помилка` | 1 |

Коди виходу:

- `0` — успіх або `--help`;
- `1` — помилка CLI, вводу/виводу або парсингу;
- `2` — математична помилка (вироджена матриця, нестабільність) або
  неузгодженість результатів.

## Обмеження

- Підтримуються лише квадратні системи з одним правим вектором.
- Використовується `Double`; для погано зумовлених систем точність обмежена
  плаваючою комою.
- Для виродженої матриці повідомляється «немає єдиного розв'язку»; програма
  не розрізняє «немає розв'язків» і «нескінченно багато розв'язків».
- Немає ітераційного уточнення, масштабування рядків або повного вибору
  головного елемента за рядком і стовпцем.
- Немає графічного інтерфейсу; це CLI-застосунок.
- Максимальний вхідний розмір — 10000, генератора — 2000.
- Прискорення залежить від кількості ядер, розміру системи та налаштувань
  RTS; на малих системах паралельний режим може бути повільнішим.
- Це навчальна реалізація, а не заміна LAPACK/BLAS.
